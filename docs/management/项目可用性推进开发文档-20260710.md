## 1. 当前可用性判断

### 1.0 产品目标

根据产品方向确认，本项目目标不是仅供开发者自用的小工具，而是面向普通用户发布的完整桌面应用。

目标体验：

- 好看的桌面解压工具：保持优雅、苹果风、扁平化的视觉风格，降低普通用户的使用门槛。
- 专业多格式工具：尽可能支持更多压缩和解压格式，并优先完善常见格式的稳定性。
- 密码压缩/解压工具：尽可能支持更多格式的密码压缩和密码解压。
- 解压密码本：密码本只用于管理压缩包密码，不按通用密码管理器标准设计，但仍需避免明文泄露、误提交和明显安全缺陷。
- 批量处理助手：支持多项目、多任务推进、任务队列、任务进度、取消、失败重试和结果追踪。
- 可发布应用：必须提供普通用户可安装、可升级、可卸载的安装包。

第一版可用版本应包含：

- 多格式解压：ZIP、7Z、RAR、TAR、GZ、BZ2、XZ，以及依赖 7z CLI 的扩展格式。
- 多格式压缩：ZIP、7Z、TAR、GZ、BZ2、XZ，后续扩展 RAR、Zstd、LZMA 和组合格式。
- 密码能力：ZIP/7Z/RAR 密码解压优先；ZIP/7Z 密码压缩优先；其他格式按底层库或 CLI 能力渐进支持。
- 密码本：新增、编辑、删除、搜索、复制、按使用频率排序、解压时智能尝试。
- 任务系统：批量添加、独立进度、并发控制、取消、失败提示、完成后打开目录。
- 安装包：Windows 安装包优先，后续再扩展 macOS/Linux。

long-compress-assistant/src-tauri/data/

## 4. P2：功能可用性闭环

### 4.1 核心用户流程

必须优先保证以下流程可用：

1. 添加压缩包。
2. 选择输出目录。
3. 解压 ZIP、7Z、TAR、GZ、BZ2、XZ。
4. 解压带密码 ZIP/7Z。
5. 添加多个任务并显示进度。
6. 取消任务。
7. 压缩单文件、文件夹、多文件。
8. 使用密码本保存、搜索、复制、删除密码。
9. 应用关闭后再次打开，设置和密码本仍可用。

面向普通用户发布时，还必须补齐：

10. 双击或右键压缩包后能进入合理的应用流程。
11. 多个压缩包批量解压时，每个任务都有独立结果。
12. 密码错误时能继续尝试密码本或提示用户输入。
13. 外部依赖缺失时有清晰提示，例如未安装 7z、WinRAR 或 unrar。
14. 解压失败时不留下半成品误导用户，或明确标记为部分完成。
15. 安装、升级、卸载不会删除用户自己的压缩包和输出文件。

每个流程都应有：

- 手工 smoke test 记录。
- 至少 1 个自动化测试或后端专项测试。
- 明确失败提示。

### 4.2 密码本数据目录改造

当前 release 逻辑中，非 debug 使用：

```rust
std::path::PathBuf::from("data")
```

这会把生产数据放到相对目录，容易随启动路径变化。

建议改为：

- Windows：`%APPDATA%/LongDecompress` 或 Tauri app data dir。
- macOS：`~/Library/Application Support/...`
- Linux：`~/.local/share/...`

完成标准：

- 开发环境和生产环境数据目录清晰分离。
- 打包后从任意工作目录启动，密码本仍写入固定 app data 目录。
- 卸载、重装、升级策略有明确说明。

### 4.3 CLI 密码传参风险

历史文档已指出：7z/unrar/WinRAR CLI 使用 `-p<password>` 时，密码可能暴露在进程列表。

建议：

- 优先使用原生库处理密码解压。
- 必须调用 CLI 时，调查是否支持 stdin、环境变量或临时受限权限配置文件。
- 对不可避免风险，在 UI 中给出能力边界，不把该路径作为高安全场景推荐。

完成标准：

- 搜索 `Command::new` 调用点，确认所有密码传递路径。
- 形成一份 `docs/security/password-cli-risk.md`。
- 对可修复路径完成替换。

## 9. 多格式能力补完路线

### 9.1 当前定位

项目已经具备“内部试用级多格式工具雏形”，但还没有达到“成熟多格式压缩软件”的交付标准。

当前已较实的能力：

- 解压侧：已覆盖 ZIP、ZIPX、7Z、RAR、TAR、GZ、BZ2、XZ、ZST/ZSTD、TAR.GZ、TAR.BZ2、TAR.XZ、TAR.ZST、LZMA，以及依赖 7za 的 JAR、APK、Office 文档包、ISO/IMG、CAB、DMG、WIM、VHD/VHDX、DEB/RPM、MSI/NSIS、CPIO 等通用格式。
- 压缩侧：已覆盖 ZIP、7Z、TAR、TAR.GZ、TAR.BZ2、TAR.XZ、TAR.ZST、GZ、BZ2、XZ、ZST/ZSTD、LZMA、RAR 方向。
- 密码能力：ZIP、7Z、RAR 是优先原生/专门处理路径；非原生密码格式可考虑自动转为 7Z AES-256 加密容器。
- 外部工具：7za 已进入内置/优先查找路线；RAR 压缩仍依赖 WinRAR/RAR 命令行，不能假装完全内置。

距离预期还差的关键闭环：

- 用户能看到并理解每种格式的能力边界。
- 前端、后端、测试对格式支持的定义一致。
- 分卷压缩进入主流程，并具备 UI、输出命名和回归测试。
- RAR 压缩依赖提示足够清晰。
- 通用格式支持必须有真实样本烟测，而不是只在 accept 列表里出现。
- 用户可见错误信息和关键日志不能继续乱码。

### 9.2 阶段一：统一格式能力矩阵

目标：建立唯一可信的格式能力定义，避免前端、后端、测试各自维护一份格式列表。

任务：

- 定义统一能力字段：`format`、`displayName`、`extensions`、`canCompress`、`canExtract`、`supportsPasswordCompress`、`supportsPasswordExtract`、`singleFileOnly`、`supportsSplit`、`requires7za`、`requiresWinRar`、`fallbackEngine`、`knownLimitations`。
- 覆盖格式分组：
  - 核心归档：ZIP、7Z、RAR、TAR。
  - TAR 组合：TAR.GZ、TGZ、TAR.BZ2、TBZ/TBZ2、TAR.XZ、TXZ、TAR.ZST、TZST。
  - 单文件流：GZ/GZIP、BZ2/BZIP2、XZ、ZST/ZSTD、LZMA。
  - ZIP 容器类：JAR、XPI、ODT、ODS、DOCX、XLSX、PPTX、EPUB、IPA、APK、APPX。
  - 镜像/安装包/系统包：ISO、IMG、CAB、DMG、WIM、VHD/VHDX、DEB、RPM、MSI、NSIS。
  - 其他 7za 兜底：LZH/LHA、ARJ、CHM、SQUASHFS/SFS、XAR、CPIO、UDF、FAT、NTFS、HFS。
- 前端格式选择、文件选择 accept、后端格式推断、测试矩阵都从能力矩阵同步。

任务：

- 压缩页按能力矩阵禁用不可选项。
- 对 RAR 压缩显示 WinRAR/RAR 依赖状态、重新检测、下载入口。
- 对 7za 兜底格式显示“需要内置或系统 7za”的状态。
- 密码压缩如果自动切换为 `.7z` 容器，必须在输出文件名和提示里明确。
- 对单文件格式 GZ/BZ2/XZ/ZST/LZMA，在多文件或目录场景下引导用户选择 TAR.*。

完成标准：

- 用户在开始任务前就能知道当前格式是否可用。
- 错误提示可读，不出现乱码。
- 批量任务中某一项失败不会阻断其他可执行任务，最终给出成功/失败汇总。

### 9.6 阶段五：发布前格式支持说明

目标：对外说明诚实、清晰、可维护。

任务：

- 写一份支持格式表，分为“可压缩”“可解压”“需要外部工具”“仅单文件”“支持密码”“支持分卷”。
- 写明 RAR 创建依赖 WinRAR/RAR，不能宣传为完全内置。
- 写明非原生密码格式会转为 7Z AES-256 加密容器。
- 写明单文件流格式不能直接打包多个文件。
- 写明缺少外部工具时的处理方式。

完成标准：

- README、应用内提示、发布说明三处说法一致。
- 用户试用前能理解当前限制。

### 9.7 推荐执行顺序

1. 先做阶段一：统一格式能力矩阵。
2. 再做阶段二：分卷压缩主流程。
3. 然后做阶段三：真实格式烟测矩阵。
4. 接着做阶段四：依赖提示和 UI 禁用规则。
5. 最后做阶段五：发布说明和用户文档。

阶段推进原则：

- 每个阶段完成后必须跑对应测试并停顿审计。
- 每个阶段单独提交，避免格式扩展、UI 文案、测试、发布配置混在一起。
- 新增格式时必须同时补：能力声明、前端入口、后端实现或兜底、测试或明确跳过理由。
