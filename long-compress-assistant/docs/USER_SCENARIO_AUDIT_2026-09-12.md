# 用户操作顺序审计与失败原因优先展示

## 基线与验收原则

基线 `master@34a439e`，版本 1.3.2、schema 8 不变。对齐最初工作区计划第 1 节：用户流程必须可见、真实引擎结果与任务/历史一致，不能把组件测试或后端直调当作安装版桌面闭环。遵循本轮用户要求：使用用户口吻描述场景，不为验收通过削弱断言、取消保护或改写失败事实。

## 本步修复

用户：“我点开失败记录，先告诉我到底为什么失败，再让我决定要不要重新解压。”

实际代码中，历史详情原先将最终错误放在来源、输出和完整解压草稿之后。用户需要向下找原因，却先看到新任务入口。这是信息顺序偏离，不是错误分类引擎未返回原因。

- 最终失败原因移至详情标题之后、指标与路径之前，明确标注标题，保留原始错误和类别/阶段。
- 诊断导出位于新草稿之前；回滚人工指引仍保留，但不抢在最终原因之前。
- 完成/取消任务不因残留错误字段而展示最终失败；旧记录未知原因不猜测。
- 不自动重试，不改变密码、清理或数据库逻辑，不删除现有验收。

新增场景测试先在旧代码上因“错误块位于草稿之后”的 DOM 顺序断言失败，再修产品代码；同一顺序断言通过。没有通过修改该断言达成通过。

## 实际证据与限制

| 场景（用户口吻） | 操作/验证方式 | 结果 |
| --- | --- | --- |
| “先说为什么失败，再让我重试。” | 挂载真实 HistoryView，筛选解压、点击失败记录，核对原因/导出/草稿顺序与原文 | 通过；组件交互，不等于桌面验收 |
| “我取消了，别把旧错误说成本次失败。” | 完成/取消状态仍携带旧错误的组件场景 | 通过 |
| “回滚没完成，到底在哪出了问题？” | 真实组件显示原始恢复路径，原因先于指引，报告保留原文 | 通过；回滚事实由测试记录提供 |
| “下载中断了，别乱试密码。” | Rust 既有真实截断 ZIP、损坏条目、缺卷、加密 ZIP/7Z 诊断回归 | 12/12；仅诊断服务，不代表本轮整条解压 UI 通过 |
| “从浏览文件开始，选下载中断的资料，再看失败记录。” | 编译当前基线的 `custom-protocol,desktop-e2e` 程序，独立数据目录，用 computer-use 打开真实文件选择器 | 未完成：工具无法稳定定位选择器控件；未提交文件，未产生真实失败历史。禁止记为通过 |

- 六组解压/历史/任务/命令回归 **88/88**，类型检查与生产构建通过。
- 首次直接跑 `vitest run src`：340 通过、5 失败，其中 4 项缺少图片测试资料；随后运行项目正式 `npm run test:unit`，由原有 pretest 准备真实图片资料，得到 **368 通过、1 失败**（共 369）。没有删除或跳过失败测试。
- 剩余失败：`CompressionView > clears only finished compression tasks from the compression center`。测试在历史保存仍在进行时要求清除；当前仓库会保留该任务。代码审查另发现页面先 `removeJobsByTaskIds`，后调用带保存保护的 `clearFinishedTasks/removeTask`，存在工作项与任务不同步风险，尚未在桌面复现。
- 桌面工具报错包括 `element 215 is not available in cached app state`，重新定位、重建会话后仍报 `call get_window_state before using this window`。按 computer-use 恢复规则停止输入，关闭本轮启动的隔离测试进程。未修改用户的真实历史库。
- `scripts/prepare-failure-user-scenario.mjs` 可生成独立的完整 ZIP、截断 ZIP、中文资料和输出目录；每次创建新目录，不覆盖旧证据。本机目录为 `test-results/failure-user-scenario-14fJ6x`；资料可重建，目录及私人桌面截图不推送 GitHub。
- 本轮没有安装版验收、全量 Rust 回归或 Release 发布。Windows 包构建 CI 仅证明构建，不替代以上失败/未完成项。

## 后续顺序（不再盲目扩展恢复引擎）

1. 压缩中心清除/单项移除与历史保存保持一致：用“我刚完成就点清除”“保存失败后我再试一次”场景验证；保留未落库结果，不取消保护来满足旧测试。
2. 恢复可用桌面操作后，从原生选文件开始执行完整包成功、截断包失败、重新下载后创建新任务三条链；核对输出内容、无密码误导、历史最终原因及应用重启。
3. 综合复查冲突覆盖、占用导致回滚、回滚不完整保留数据的主流程；区分真实故障注入与人工构造记录。
4. 以上问题关闭后再冻结补丁范围、决定版本与发布。本轮不能认定阶段全部完成。
