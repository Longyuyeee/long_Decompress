# C-03.3.1 视频单命令安全管线审计

日期：2026-08-29

范围：统一任务命令、权威重规划、取消/输出锁、阶段事件与验证后发布

结论：**C-03.3.1 已完成；后端现在只有一个可调用的视频执行命令，且该命令不会暴露暂存结果。视频工作区执行按钮仍保持关闭，待 C-03.3.2 接入统一任务 UI、最终指标和历史后再开放。**

## 1. 实现与最初需求对齐

| 要求 | 实际实现 | 状态 |
| --- | --- | --- |
| 不复制任务系统 | `compress_video_file` 复用 `commands/compression.rs` 唯一的取消注册表和输出占用锁；取消仍走 `cancel_compression` | 通过 |
| 单个安全命令闭环 | 命令内部固定执行“冻结引擎校验 → 重新探测/规划 → 编码到暂存 → 完整验证 → 原子发布”，调用方拿不到未验证暂存路径 | 通过 |
| 执行时不信任旧计划 | 后端重新读取真实源文件并重建计划；有损流变化必须与前端提交的已确认列表完全一致，否则返回 `VIDEO_COMPRESSION_STREAM_CHANGES_CONFIRMATION_REQUIRED` 且不启动编码 | 通过 |
| 真实进度与心跳 | 继续使用统一 `task-progress`；扩展当前媒体时间、速度倍数、临时输出大小/比例、ETA 和心跳字段。心跳重复最后一份真实快照并标记 `still-encoding`，不制造新百分比或字节进度 | 通过 |
| 可审计阶段 | `task-log` 和 `task-progress` 均按 `Probing → Encoding → Validating → Publishing` 发出；前端统一 task store 已能保存媒体字段 | 通过 |
| 全阶段取消 | 编码继续使用 Job Object；探测和验证由 25 ms 取消竞争包裹，Future 被取消时 `kill_on_drop` 终止 ffprobe，暂存所有者 drop 清理文件；发布边界继续读取同一取消令牌 | 通过 |
| 最终事实唯一 | 命令只返回 `PublishedVideoOutput`：输入/输出字节来自磁盘，容器、时长、音视频编码和尺寸来自发布前完整验证 | 通过 |
| 源文件保护 | 当前视频 UI 没有“回收源文件”选项，命令不擅自消费全局归档删除设置；成功与失败测试均确认源文件保留 | 通过 |

本节点没有把估算大小写入最终结果或历史，也没有因 FFmpeg 报告 `progress=end` 就标记任务完成。只有 C-04 验证和共享原子发布成功后命令才返回。

## 2. 审计纠偏

最初考虑用单个布尔值表示“用户已确认流变化”。实际代码审计后拒绝该设计：如果规划完成后源文件被替换，旧布尔值可能放行新出现的字幕、多音轨或章节丢弃。现在请求携带用户看到的完整 `confirmedStreamChanges`，执行时与重新探测生成的权威列表逐项比较；任何偏移都要求重新规划和确认。

旧媒体架构门禁把 `compress_image_file` 到 `cancel_compression` 的整个源码区间都视为图片命令。加入视频事件后它把真实视频进度误判为图片伪进度。本节点将切片收紧到真实图片命令边界，并新增视频单命令、统一锁/取消、重规划、验证、发布和心跳的静态契约，没有放宽图片“无可信回调就不发百分比”的规则。

前端事件测试还发现 FFmpeg 解析器公开 `0–100` 百分比，而现有统一 `task-progress` 约定传输 `0–1` 比例。如果原样发送，42.5% 会被 task store 夹成 100%。映射边界现已显式除以 100；视频解析器及媒体专属字段仍保持原始事实语义。
