# B-03.1 单文件图片编码与发布事务审计

审计日期：2026-08-28

开发分支：`codex/archive-media-roadmap`

进入基线：`f4ea25b`（B-02 图片工作区与系统选择路径收口）

公开版本：`1.1.14`（本步骤不升版、不发布）

## 1. 结论

B-03.1 完成一个可独立审计、但尚未连接界面的后端闭环：JPEG、PNG、WebP 输入先由内容魔数与真实解码器共同确认，编码只写目标目录内的唯一事务暂存文件，完成后重新完整解码并验证输出格式、编码像素矩阵、EXIF 方向、应用方向后的可见尺寸、帧数和 Alpha，最后才按用户大小策略调用 B-00 的共享原子发布事务。

本步骤没有把 B-03 或图片压缩整体标记为完成。输出格式转换、缩放、非方向元数据逐字段保持/移除验证、运行任务取消注册表、容量预检、发布成功后回收源文件与最终 NSIS 增量仍是 B-03.2 的阻断项；B-04 的进度、日志、历史也未提前实现。前端执行按钮继续禁用。

## 3. 依赖准入纠偏

B-00/B-01 的 `integrationAllowed=false` 是进入产品运行时前的冻结条件，不是永久条件。B-03.1 按原计划将以下精确依赖改为 `runtime-admitted-b03-service`：

- `libcaesium = 0.21.0`，关闭默认功能，仅启用 `jpg,webp`；
- `oxipng = 10.2.0`，关闭默认功能，仅启用 `parallel,zopfli`；
- `image = 0.25.10`，关闭默认功能，仅启用 `jpeg,png,webp`，作为独立重解码验证器。

准入门禁现在只允许上述三个图片依赖进入运行时，锁定 Cargo 声明和 Cargo.lock 版本，并继续禁止 `gifski`、`imagequant`。FFmpeg 与 qpdf 保持 `integrationAllowed=false`。新增直接使用的 `image` 依赖也补录了 crate 字节数、SHA-256、双许可、feature 边界和安全责任，避免把传递依赖当作未经治理的隐形直接依赖。

全量审计还发现媒体架构扫描只识别驼峰 `imageCompression`，会漏掉 Rust 惯用的 `image_compression` 文件名；门禁已扩大为同时覆盖驼峰、下划线和连字符命名，新服务现被纳入禁止绕过共享发布/历史/回收边界的扫描。

真实依赖复验首次运行时，crates.io 对没有 User-Agent 的审计下载返回 HTTP 403；补头后当前 Node 网络层下载 FFmpeg/qpdf 又会在无数据时停滞。下载器已增加固定产品审计标识、二进制 Accept、60 秒超时、`.part` 原子缓存、三次有界重试和 Windows `curl.exe` 回退；最终 5 个锁定制品全部通过字节/SHA-256，FFmpeg 继续通过签名验证，qpdf 继续通过校验清单与真实运行验证。来源和完整性条件未放宽。

## 4. 真实证据

- EXIF JPEG：15,788 B 输入，编码矩阵 640×360，Orientation=6，方向后可见尺寸 360×640；编码后重解码事实一致并成功发布。
- 透明 PNG：真实无损优化后重新解码，Alpha 保持。
- WebP：真实执行取消/结果不更小策略，目标与事务暂存均不残留。
- 扩展名边界：JPEG 字节复制为 `.bin` 后仍按魔数成功处理；最终目标扩展名与真实格式不符时失败关闭。
- GIF：真实三帧样本在暂存前明确拒绝，不创建输出。
- 目标保护：已存在目标字节保持不变；共享发布事务另有发布时目标竞态测试。

## 5. 已知边界与下一步

1. 当前服务只处理同格式、保持尺寸输出；不能把前端已有的格式与缩放配置静默忽略，因此尚不连接命令和按钮。
2. `preserve_metadata` 已传给编码器，方向信息作为视觉完整性数据始终保持；除方向外的 EXIF/ICC/PNG ancillary chunks 仍需在 B-03.2 做逐字段正反验证后才算完成元数据策略。
3. 编码器是同步调用，取消可在编码前和编码后生效并清理，但还未接入现有任务取消注册表；B-03.2 需要把阻塞编码放入受控后台任务并复用容量预检。
4. B-01 的 1,077,127 B 是隔离候选压缩载荷，不是产品 NSIS 增量。正式依赖已经进入产品 Cargo，但最终 NSIS 前后对比尚未测量，B-03 不得关闭。
5. 下一接续点是 B-03.2，不进入 B-04，不提升版本，不更新 Release。
