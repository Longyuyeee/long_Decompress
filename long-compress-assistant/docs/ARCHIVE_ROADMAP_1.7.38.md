# v1.7.38 规划 · 流式 ZIPX（XZ）丢目录部分取回

状态：已完成功能封板；接续普通多帧 Zstandard，回到其他已支持方法的恢复缺口。本软件已有正常 ZIPX / XZ 读写，本期不增加格式数量。

可行性已核对：7-Zip 26.04 通过不可寻址 stdout 实际生成 method 95、flags 8、本地压缩/展开尺寸均为 0 的 ZIPX 原件。Python 标准 liblzma 从实际 XZ 流解码到结束，消费量 160 字节、展开 32000 字节、CRC 和描述符一致，未修改压缩内容。样本及探测见[证据](evidence/zip-zstd-multiframe-1.7.37/next-xz-probe.json)。这只证明独立来源和实际流边界可确认，本版已接入单流恢复并完成检查。

1. 固定独立流式原件，先处理未加密、未知本地尺寸的 method 95 单 XZ 流。使用已有 xz2 / liblzma 的消费量与 StreamEnd，确认块校验、索引/尾部及累计展开量和 ZIP CRC，再匹配准确位置的描述符；不扫描正文标记猜测边界。
2. 接通文件、空文件、明确目录和混合方法；普通/ZIP64、有/无签名和完整数字切片以真实原件或明确标记结构控制确认。损坏、截断、矛盾或未知边界停止，只另存之前已完整确认的文件，原清单仍未知。
3. 沿用暂存、新包整体验证、已确认日期传递、结果/历史和失败重试，保留取消与资源上限。界面、单条展开、多选弹窗及等宽双栏保持，只检查新增和受影响流程。

完成标准：声明范围内的成员完整取回，新包及本软件最终目录的内容/路径和可确认日期经独立工具核对，坏成员不产生半个文件，原件不变，既有方法保持。

多个 XZ 流、流填充、特殊滤镜/字典组合以及密码未知边界先按来源另期确认；不承诺全部 ZIPX 专有算法。Zstandard 可跳过帧/外部字典、历史 method 20、跨缺口扫描、恢复记录、ALZ / EGG 原生密码/块分段、更宽日期与 NTFS 亚秒等仍为后续未完成项。

完成记录：5 项新增原生最终、2 项相关旧组与 34 份新包 / 120 个条目严格独立核对通过。零字节来源的四次外部工具警告单独记录，未计通过；已确认日期沿既有 DOS/UT 范围。见[封板](ZIP_XZ_RESCUE_FREEZE_1.7.38.md)，下一阶段 [v1.7.39 XZ 多流与合法填充](ARCHIVE_ROADMAP_1.7.39.md)仅规划。
