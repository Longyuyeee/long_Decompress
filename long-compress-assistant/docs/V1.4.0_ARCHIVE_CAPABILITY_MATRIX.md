# v1.4.0 归档组合能力基线（ARCH-01）

> 2026-10-11 当前进度：ZIP 编码已接入创建、读取、校验及前端选项；数字卷原生校验和原生创建→临时 ZIP→切卷已接入引擎，包含目录、空目录、多文件和密码专项。外层任务与 UI 的目录/密码分卷限制尚未解除，整组输出、临时空间与进度仍待整合，不能宣称用户端已完整支持。下方表格及早期进度记录保留为历史基线，以开发交接最新节为准。

> 最新进度：按用户确认实现显式 Windows 本地密码编码底层，UTF-8 仍为默认。实际系统代码页转换及不可表示字符拒绝测试通过，兼容模式中文密码的原包和数字卷由本机 7-Zip 读取成功。尚未接入产品任务/UI，默认 UTF-8 的原失败用例保留；不是完整产品修复或发布验收。

> 最新根因：7-Zip ZIP 解密按 CP_ACP 转换密码，本机 ACP=936；应用原生创建使用 UTF-8。人工 CP936 密码字节对照原包和分卷均通过独立读取。尚未更改产品编码策略，待用户确认显式兼容模式；不能以对照成功替代原 UTF-8 失败用例。来源与复验命令见开发交接最新节。

> 2026-10-11 后续实测更新：新增数字切卷底层尚未接入产品。中文密码 AES ZIP 原生读取通过，但本机 7-Zip 26.02 对原包及数字卷均报密码错误，ASCII 对照通过。失败用例保持启用，当前不是可发布状态。以下 ARCH-01 表格描述审计时基线，不覆盖此新增失败证据；详见开发交接最新节。

审计日期：2026-10-11；产品基线为 UI-06 提交 `f3f061d`。这是实际代码与专项测试基线，不是 1.4.0 发布验收。旧版 A/B 桌面证据仍由 [格式支持等级](FORMAT_SUPPORT_LEVELS.md) 管理；不能把格式级 A 推导成所有编码、加密和分卷组合均为 A。

## 当前创建/读取矩阵

“代码路径”表示已定位实现，不表示本轮重新做过安装版闭环。“待组合实测”不得宣传为完整支持。

| 格式/编码 | 创建与密码 | 分卷创建 | 读取及证据边界 |
| --- | --- | --- | --- |
| ZIP / Deflate | 原生普通 ZIP、AES-256 ZIP；无 ZipCrypto 创建选择 | 仅无密码普通文件，可多文件；7-Zip 输出 `.zip.001` 数字卷 | 原生读取；本轮真实数字卷由 7-Zip 从首卷解压并比对载荷，不是 Tauri 安装链 |
| ZIP / Store、BZip2、Deflate64、LZMA、XZ、Zstd 等 | 当前普通创建路径固定 Deflate，不因依赖支持解码就提供创建 | 不额外承诺这些编码的分卷创建 | `zip_aes` 启用了多编码特性；逐编码 × AES/ZipCrypto × 分卷互操作仍待补齐；ZIPX 仅别名，不证明所有 ZIPX 编码 |
| ZIP / ZipCrypto | 当前无创建入口；不自动将 AES 降级 | 不支持创建密码分卷 | 原生读取及已有错误密码测试路径；本轮未重跑所有密码读取组合 |
| 7Z / LZMA2 | 原生创建，内容可 AES 加密，支持固实；当前无独立文件名加密选项 | 能力表明确关闭 | 原生/后备读取；文件头加密读取已有代码测试，但不等于已提供文件名加密创建设置；分卷组合待实测 |
| RAR | 创建须用户提供 WinRAR/Rar.exe；密码创建还要求已有显式参数授权，命令使用 `-hp` | 能力表关闭 | 既有只读能力；RAR 版本、文件头加密、旧/新分卷分别验，不因识别后缀直接认定通过 |
| TAR、TAR.GZ/BZ2/XZ/ZST | 正常创建；这些容器本身无密码 | 不支持 | 既有创建读取路径；设置密码须选择 AES 包装或明确 7Z 输出，不冒充原格式原生加密 |
| GZ、BZ2、XZ、ZST/ZSTD、LZMA | 单个普通文件；目录/多文件拒绝 | 不支持 | 既有流格式读取路径，TAR 组合与单文件流须分开描述 |
| TAR.AES、TAR.GZ/BZ2/XZ/ZST.AES；GZ/BZ2/XZ/ZST.AES | 应用现有 AES 包装路径；流格式仍单文件 | 不支持 | 不能当作通用 ZIP/7Z AES；不承诺其他归档软件可读取本包装 |
| WIM | 引擎须报告可创建；拒绝密码 | 拒绝 | 既有引擎路径；本轮未重新测 WIM 安装链 |
| 其他公开只读格式 | 不开放创建 | 不开放创建 | 沿用 FORMAT_SUPPORT_LEVELS.md 的旧版证据；本轮不提升等级、不扩大白名单 |

## 关键执行约束与偏差

1. `src/utils/compressionFormat.ts` 与后端 `services/compression_format.rs` 中 ZIP 的密码、分卷布尔值是独立能力，不能相乘。`CompressionService::compress` 还会调用 `validate_compression_io_paths`，拒绝密码+分卷、目录+分卷；仅调用格式校验通过不代表可以执行。
2. `services/split_compression.rs` 再次拒绝上述组合，并调用 7-Zip `a -tzip -v…b`。这是数字切片，不是 PKZIP `.z01/.zip` 多卷；已有测试名称中的 “standard split” 不应成为跨格式宣传依据。
3. `services/native_compression/zip.rs` 固定 Deflate，密码路径使用 AES-256；已移除快速打包，不应在新矩阵中继续承诺抽样 Store。
4. `services/native_compression/seven_zip.rs` 配置 LZMA2 与内容 AES；`CompressionOptions` 没有独立文件名加密选择。读取文件头加密的测试不能代替创建能力。
5. `services/split_archive_detector.rs` 能识别 ZIP、RAR、7Z 和通用数字卷等命名；识别/排序不是完整性证明，尤其无法仅凭连续编号证明末卷存在。
6. 审计发现 `compression_capabilities_regression.rs` 全字段初始化漏了兼容字段 `fast_pack`，导致该专项无法编译；已补 false，并纠正“ZIP 密码通过 CLI”的过时注释。产品能力未因此改变。

## 本轮可复现证据

在 `long-compress-assistant` 运行：

```powershell
cargo test --manifest-path src-tauri/Cargo.toml --test compression_capabilities_regression --test split_compression_test
```

- 15 项能力回归、8 项分卷回归通过。包含现有别名、单文件限制、密码输出约束、实际分卷 ZIP 创建与字节比对、既有输出保护，以及新增非 ZIP 分卷拒绝、密码/目录分卷拒绝且不产生输出/不改源文件。
- 本机真实分卷回解输出引擎为 7-Zip 26.02；本轮未用其版本信息推断其他机器部署情况。
- 这些拒绝用例固定的是**当前基线**，不是永久禁止需求。ARCH-02 实现新能力时应以真实成功闭环替换相应拒绝断言，保留失败残留和源文件保护检查。
- 不涉及用户真实归档、历史或已安装应用；没有 UI 改动，因此没有新增页面验收结论。
