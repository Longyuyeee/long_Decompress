## 5. 尚未完成与风险

恢复验证首先发现 Windows CRLF 门禁误报以及图片桌面门禁不必要依赖完整 FFmpeg 媒体夹具；两项已完成纠偏并通过真实图片基线，证据见 [B02_VALIDATION_INFRASTRUCTURE_AUDIT.md](B02_VALIDATION_INFRASTRUCTURE_AUDIT.md)。

1. 资产协议修正后的隔离 Release 二进制尚未重跑完成 `test:e2e:desktop:image-workspace`；这是 B-02 当前明确阻断项。
2. 当前桌面门禁通过测试桥注入真实文件，仍需补一次用户可见的原生选择/拖放操作，验证文件路径、拒绝提示和焦点行为没有被测试桥绕过。
3. 原图预览授权目前只允许 JPEG、PNG、WebP，且要求魔数与扩展名一致。这是有意的安全边界；若以后支持无扩展名图片或 TIFF，必须先更新依赖与样本审计，不能放宽成任意本地文件资产访问。
4. B-02 不执行编码，因此没有实际输出大小、压缩率、结果图或历史任务；这些只能由 B-03/B-04 的真实事实来源提供。
5. 本阶段不应提交 `target`、`dist`、测试截图或本地安装包等生成物。

## 6. 接手后的严格顺序

1. 在应用目录执行隔离桌面构建：先设置 `VITE_DESKTOP_E2E=1` 构建前端，再在 `src-tauri` 使用 `cargo build --release --features custom-protocol,desktop-e2e`；不得覆盖正式安装态。
2. 设置与当前 WebView2 匹配的 `EDGE_DRIVER_PATH`，运行 `npm.cmd run test:e2e:desktop:image-workspace`。
3. 对比预期和实际：三种允许格式都应显示真实尺寸和原图；GIF/PDF 应明确拒绝；1100×720 与 760×560 均无横向滚动；设置区与预览区保持可操作；归档与图片队列切换互不污染。
4. 逐张检查 `test-results/desktop-e2e/image-workspace-1100x720.png` 和 `image-workspace-760x560.png`。若失败，必须记录首次实际、原因和修正后结果，不得只调整选择器绕过产品问题。
5. 用系统文件选择器或真实拖放补测至少一个 JPEG 和一个 GIF，确认用户路径与测试桥结果一致。
6. 桌面门禁通过后，再执行全量前端测试、类型检查、Rust 测试/Clippy、媒体架构门禁和发布身份门禁，更新本审计为 B-02 收口；仍不升版。
7. 只有 B-02 收口后才进入 B-03：接入已审计图片引擎和共享发布事务，生成可重新解码的真实输出。大节点 B 完整通过 B-03 至 B-05 后，才允许提升补丁版本并更新 README、Release 与安装包。

## 7. 需求与偏移审计

本阶段仍以归档压缩/解压稳定性为基线，没有修改现有归档执行路径；图片草稿复用现有压缩 store，并以独立集合避免污染归档草稿。暂停审计发现并纠正了“新建图片 store 绕过 B-00 统一任务边界”的实现偏移，也补强了对应静态门禁。没有把视频/PDF 计划节点伪装成完成，也没有提前引入未经发布审计的编码器。当前剩余偏差不是产品方向偏移，而是 B-02 桌面证据尚未闭环；继续开发必须先完成第 6 节的真实复验，不能直接进入 B-03 或升版。
