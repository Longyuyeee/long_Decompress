# 工作区密度、文字完整提示与双栏布局审计（2026-09-03）

## 目标与结论

本轮在公开 `v1.2.6` 后续开发分支上关闭三项界面问题，不提升版本、不打包、不创建 Release：

1. 实际发生省略的单行文字，鼠标悬停或键盘聚焦时应能看到完整文本。
2. 解压中心、压缩中心、特殊压缩的标题区应向文件浏览器的紧凑密度对齐，把空间还给中间任务区，并让底部操作区靠近工作区下沿。
3. 双栏文件浏览器在窄窗口中仍必须保持左右两栏，不得切换成上下排列。

三项均已实现并通过浏览器与真实 Windows Tauri 窗口审计。用户正在运行的 `E:\Long\Long解压\Long解压.exe` 未被停止或替换。

## 实现审计

### 1. 省略文本完整提示

- 新增统一的溢出标题安装器：只对计算样式为 `text-overflow: ellipsis` 或带 `truncate` 类、并且真实 `scrollWidth > clientWidth` 的元素设置原生 `title`。
- 仅在 `mouseover` / `focusin` 时计算，避免为未省略内容制造无意义提示；已有显式 `title` 不覆盖。
- 文件浏览器名称、大小、修改时间另保留稳定的显式标题，保证最常用列表字段无需依赖下一次布局计算。

预期：只有真实省略的文本出现完整提示，已有业务提示不被替换。实际：单元测试覆盖真实溢出、非溢出和已有标题三种边界，全部通过。

### 2. 三个工作区密度对齐

- 解压中心与压缩中心外层留白由大间距调整为紧凑间距，标题缩为 `text-xl / md:text-2xl`，副标题同步收紧。
- 特殊压缩标题、Tab 高度、工作区壳间距同步缩小；Tab 仍保持在标题右侧。
- 解压中心底部输出操作条减少纵向内边距，三个页面的主壳均增加稳定测试标识。

预期：标题更靠上、底部更靠下、中间任务区更高，页面本身不新增纵横溢出。实际：Chromium 在 920×620 下验证顶部间距不超过 17 px、标题区不超过 58 px、底部间距不超过 17 px；真实 Tauri 的 920×620 与 760×520 截图中，解压/压缩标题均保持紧凑，中间详情仍为内部滚动。

### 3. 双栏文件浏览器永远左右排列

- 删除小于 900 px 时改为单列两行的规则；所有宽度均使用两个 `minmax(0, 1fr)` 列和一个内容行。
- 900 px 以下只压缩工具栏、表格列和操作按钮；620 px 以下进一步隐藏低优先级列和按钮文字，不改变双栏方向。
- 窄宽工具栏使用自身横向滚动能力，文件浏览器根容器保持无横向溢出。

预期：920、760、390 px 三档都存在两栏，顶边对齐，右栏位于左栏右侧，根容器横向溢出不超过 1 px。实际：Chromium 三档全部满足；真实 Windows Tauri 在 920×620、760×520 两档均满足并生成截图：

## 验证结果

- `npm run type-check`：通过。
- `npm run test:unit -- --run`：52 个测试文件、290/290 通过。
- `npx playwright test e2e/app.spec.ts --project=chromium`：13/13 通过。
- `cargo build --release --features custom-protocol,desktop-e2e --manifest-path src-tauri\\Cargo.toml`：通过。
- `npm run test:e2e:desktop:file-manager`：真实 Windows Tauri 双栏、真实右键、复制、移动和属性链路通过。
- `npm run test:e2e:desktop:responsive-layout`：真实 Windows Tauri 920×620 / 760×520 解压与压缩响应式门禁通过。

桌面门禁首轮发现两项测试自身时序/文案滞后：精简卡已显示“存储预检”而脚本仍限定“目标存储预检”；特殊压缩路由入场动画尚未结束就测量壳体。门禁已改为兼容当前精简文案，并在测量前等待入场/弹窗动画稳定，随后完整重跑通过。没有用放宽布局断言来掩盖失败。

## 接续点

- 当前属于 `v1.2.6` 发布后的未升版 UI 修复，应先提交、推送并等待 CI；没有用户授权时不要打标签或覆盖公开 Release。
- 如果继续优化窄窗口，下一优先级是压缩任务展开详情的信息密度；该区域在 760×520 下仍较拥挤，但本轮没有改变其业务结构，不应把它误写成本轮回归。
- 后续任何省略文本组件默认由全局溢出标题机制兜底；业务含义不同的显式提示继续使用组件自己的 `title`。
