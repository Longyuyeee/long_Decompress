## 3. 本次发现和纠偏

### A. 已确认：RAR 错误文案分类过宽（高优先级）

`compression_service.rs:1960` 将 `archive_requires_password` 的所有 RAR 错误统一包装为“RAR 文件损坏或不完整”。但 `universal_engine.rs` 的 `requires_password` 会返回进程启动、读取和检测超时异常；这些并不能证明文件损坏。

影响：用户可能因工具异常、权限或慢设备问题被建议重新下载有效文件。应保留原始原因，分别输出损坏、缺卷、源文件变化、权限、超时、引擎不可用和未知错误。此处是代码路径确认，未在本轮制造权限或超时现场。

### B. 已确认存在判断缺口：密码提示优先于其他错误（高优先级）

`universal_engine.rs:298` 先匹配 stderr 中的 `wrong password`、`data error in encrypted file` 等文本，随后才处理非零退出。因此同时含密码提示与损坏提示的输出仍会被判为“需要密码”。v1.3.2 的已通过样本主要覆盖“局部 Encrypted 元数据 + 非零退出”，不等于覆盖所有混合错误。

此外，`requires_password` 找不到 7z 时返回 `Ok(false)`，把“无法检测”表达为“未加密”。应增加未知/检测失败状态。混合输出实际触发范围需用真实引擎输出与固定样本补证，不能声称本周用户又遇到了该问题。

### C. 历史保存存在待验证竞态与可见性缺口（中优先级）

`src/stores/task.ts:98` 每次保存直接发起 IPC，同任务的 Promise Map 只保存最新引用，没有串行等待；`failTask` 可在已经 failed 后补充原因再次保存。后端以 `ON CONFLICT(id) DO UPDATE` 覆盖记录，未见记录修订号约束。若旧快照后到达，可能覆盖较新的原因；这是代码推导的风险，本轮没有复现乱序覆盖。

同处保存失败仅 `console.warn` 并返回 false，用户缺少直接可见的“历史未保存”提示。建议定向验证乱序与失败后重试，确保保存最新终态，避免误称 v1.3.2 已保证所有环境中绝不丢原因。

### D. 历史页面还不能有效帮助用户处理失败

`HistoryView.vue` 当前有状态/类型/时间筛选、详情、删除；检索字段不包含 `errorMessage`，没有历史详情中的重建任务和诊断导出入口。错误是字符串，没有独立失败阶段、类别和建议动作字段。500 条记录、200 条日志等上限已在后端存在，导出应明确覆盖范围。

旧记录缺失的原因仍不能凭猜测补写。重试应新建任务、关联原记录，并提示源文件缺失或改变，保留真实历史。

### E. 文档与发布首页失步（本轮纠偏）

仓库根 `README.md` 的徽标和当前版本仍为 v1.2.7，而 `long-compress-assistant/README.md` 为 v1.3.2。旧增强路线仍保留许多“等待 PR”和“推荐实施顺序”快照，直接照旧列表开发会重复建设。

本轮更新根 README 当前版本与本次路线入口；在增强路线、文档导航和交接文档顶部登记新基线。历史审计保留，不回写旧测试结果。后续发布应同时核对两个 README 的当前版本。

## 5. 建议版本顺序与验收

下列是规划候选，不是已经实现或已经批准的发布时间。补丁版本先按既有 1.3.2 → 1.3.3 递增；后续功能批次是否归入 1.4.0，按实际范围收口时确定，不为凑版本扩展功能。

### 第一步：v1.3.3 候选——错误分类与失败记录可靠性

1. 建立统一错误类别、失败阶段、用户摘要、引擎原始详情和可重试条件，兼容旧字符串记录。
2. 修正上述 RAR 一律损坏、混合提示、引擎缺失三个检测边界；未知原因如实说明未知。
3. 验证并处理同任务保存乱序，提供历史保存失败提示与可恢复重试。
4. 使用损坏、错误密码、缺卷、输入变化、超时/权限、输出失败的针对性矩阵验证；真实归档验证与可控异常测试分别记录。

验收：终态显示实际类别、阶段和最终原因；错误不会被误导成密码或损坏；重新打开历史仍保留最新原因。冻结范围后提交、推送并更新发布说明。

### 第二步：v1.3.4 候选——从失败到处理的完整操作

1. 历史按失败类别筛选，并支持错误正文检索、复制摘要和导出诊断报告。
2. 按原因提供“重新选择源文件”“更换输出目录”“补齐分卷后重试”“打开诊断”等动作。
3. 复用任务配置重建待执行任务；关联原任务，明确旧记录无法恢复的配置，不直接以猜测配置启动。
4. 展示缺卷编号和输入稳定性状态，按格式能力决定可用检查；对正在下载的文件给明确下一步。

验收：实际失败 → 查看原因 → 完成处理 → 新任务成功 → 重启查到两次结果；对损坏归档不建议无意义重复试密码。

### 第三步：后续功能版 A——浏览与诊断效率

1. 在现有双栏中补常用位置/最近目录，统一磁盘文件和归档内文件的操作可用性说明。
2. 根据真实大目录测量决定分页/虚拟列表和缩略图按需加载，避免每次浏览先完整读取归档。
3. 将既有 ZIP 诊断/修复接到失败任务；呈现已恢复、未恢复、无法确认的条目，而非只有成功提示。

验收：常用任务减少重复路径选择；大目录持续可操作且可取消；修复结果可与源归档核对。已有嵌套浏览、受限预览和选择性解压继续复用。

### 第四步：后续功能版 B——智能压缩和特殊压缩补强

1. 归档智能分析说明预计节省、兼容性与速度取舍，区分预计值与最终实测；已有 JPEG/视频等低收益输入给建议。
2. 视频增加用户目标体积模式：结合时长和音频预算估算，明确误差；不能保证单次编码严格命中。
3. 图片/PDF 统一输出变大或节省极小时的处理选项与前后对比，复用现有指标和发布策略。

验收：质量/尺寸/目标体积设置确实影响引擎计划；结果按真实输出计算；不为了达标静默丢弃音轨、透明度或文档内容。先完成软件编码体验，再考虑硬件编码独立试验。

### 第五步：后续功能版 C——模板与重复工作

1. 在现有模板和目录监控基础上增加运行历史、重复来源识别及遗漏原因呈现。
2. 先提供一键复用和按需执行，再评估定时执行、错过计划补跑及重启后的恢复策略。
3. 计划任务仍进入统一队列，沿用用户并发和输出冲突规则。

验收：重复扫描不重复提交；应用重启、文件修改、输出目录不可用都有明确记录；不把暂停后的继续与崩溃后的断点恢复混为一谈。

### 第六步：独立性能方向——有数据后再调整默认值

1. 先测本机真实大文件/小文件、同盘/跨盘、不同并发，记录总耗时、CPU、内存和 UI 响应。
2. 有真实 HDD/网络盘条件时扩展；没有条件时明确缺少样本，不要求为了常规功能换电脑。
3. 仅在同样本对比证明收益后启用可撤回的调度策略；默认并发暂不因 NVMe 单机结果改变。

验收：吞吐收益与界面响应均可复核，取消和终态结果保持正确。该方向可以单独推进，不阻塞前五步。
