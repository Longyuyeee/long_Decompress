# 视频/PDF 切页控制：用户场景修复

## 需求与排序

用户正在处理视频/PDF，切到历史再回来，必须还能看到原任务并取消，不能重复执行。优先处理上版审计已有明确代码证据的跨页风险，再接失败处理动作；没有扩张媒体引擎或恢复引擎。

## 复现与修改

- 组合函数的新实例无法取消旧实例正在执行的任务；两个取消场景期望调用原任务取消，实际调用次数为 0。
- 输出路径规划阶段 `activeTaskId` 为空，第二批次未被拒绝，两个防重复场景在旧代码上超时。共四场景先红后绿。
- 视频/PDF 使用按 task store 和 workload 隔离的内存会话，规划、执行及历史保存全过程持有运行锁，外层 finally 释放。页面组件不再自行复位运行态。
- PDF 文件列表、配置和输出目录移至非持久化 Pinia store；重启不恢复未运行草稿，切页清空未提交的密码输入，不保存密码。
- 保留取消后等待后端清理及终态落库，不把用户切页当作取消，不自动重跑任务。

## 第二步：真实切页发现视频取消残留

- 回归真实复现：切页后取消视频，历史已为 cancelled、FFmpeg 已退出，但仍留下约 28 MB 的 `.video-encode-*` 暂存文件。没有删除或放宽原无残留断言。
- 原因：编码完成后的 ffprobe 验证被外层取消 future 丢弃；kill-on-drop 尚未等进程释放 Windows 文件句柄，暂存对象的 Drop 已执行并删除失败。
- 改为验证内部感知取消，终止并等待 ffprobe 退出、回收输出管道后才返回，随后暂存对象清理。正常验证、输出上限和超时语义保留。
- Windows 实际子进程独占文件测试证明取消返回后可以立即删除文件；取消前不启动进程测试通过。视频输出验证 5/5、严格 Clippy 通过；完整前端 387/387、Rust 库 405 通过/12 忽略。
- 修复后真实视频和 PDF 均能切历史页再返回取消，源哈希不变、无最终输出；视频原暂存残留断言已通过。继续核对重启历史与 PDF 暂存。

### 脚本纠偏（不改变产品）

- 运行时工具栏用取消按钮替代开始按钮，原新增断言错误地等待“禁用的开始按钮”；改为严格断言开始按钮不存在、取消按钮可用。
- 切页必须等待历史控件实际可见，避免点中离场组件；PDF 返回后等待可见文件名，不用空文本或隐藏 DOM 代替用户可见状态。
- 正式单测前置的 images-only 夹具生成会重建共享夹具目录，因此完整媒体夹具必须在单测后重新生成，不能把缺少 PDF 夹具当作产品错误。
