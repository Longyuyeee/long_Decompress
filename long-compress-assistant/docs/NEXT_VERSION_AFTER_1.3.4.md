# 1.3.4 后续开发顺序

本轮已闭合视频/PDF 跨页控制风险，并在真实使用顺序中修复视频验证期取消残留。以下均尚未实现，下一版本号与范围在验收前不作完成承诺。

1. **失败之后能做什么**：先对照结构化分类与现有历史草稿/完整性诊断入口，给损坏、缺卷、权限、目标占用分别提供对应操作。未知原因保持未知；所有重新执行都需用户确认并创建新任务，不改旧记录、不自动试密码。
2. **历史保留与查询**：后端保存时会清理 500 条之外记录。先定义保留策略和迁移，再做查询分页；不能只加加载更多，也不能承诺找回已被清理的历史。
3. **未保存结果重启恢复**：持久待保存队列、幂等 ID、落库成功再清理。覆盖数据库故障、退出、重启与重试保存，绝不自动重跑压缩。
4. **任务配置重建**：版本化非敏感快照，明确可恢复与待确认参数，不保存明文密码。
5. **媒体回归继续补强**：本版新门禁覆盖两类各自切页取消和重启历史，不把结果扩写为所有媒体组合并发、默认应用或原生选择器都已重验。下一轮有具体改动时补对应组合。

流程：实际代码核对→用户口吻场景和预期→复现→修复→回归→审计文档→推送。单测 CI 门禁的本地提交 `02f3791` 仍需 workflow 权限，不是已生效的云端门禁。

## 首项的代码基线和验收拆分

`src/utils/taskFailure.ts::getTaskRecoveryGuidance` 当前只为 `rollback-incomplete` 返回步骤；`HistoryView.vue` 已有最终原因、诊断导出和 `HistoryExtractionDraft`。因此下一轮应扩展分类指引并衔接已有草稿，不重复造一套重试执行链。

| 用户说法 | 需要新增的指引/入口 | 必须保留的边界 |
| --- | --- | --- |
| “提示损坏后，我该怎么办？” | 解释重新获得完整来源，再定位到重新选择文件/诊断入口 | 不把损坏引向试密码，不覆盖源包 |
| “到底缺哪个分卷？” | 展示已保存的缺卷事实，补齐后由原草稿流程重新检测 | 不猜测缺失名称，不直接重跑 |
| “目录不能写，能换个地方吗？” | 按已保存阶段区分来源读取与输出提交问题，引导确认本次输出目录 | 不把来源权限问题误当成输出权限，不自动提权 |
| “还是不知道原因” | 保留原始详情和未分类状态，提供诊断导出 | 不编造原因或宣称已修复文件 |

先写分类与旧记录兼容测试，再写页面可见操作测试，最后用真实损坏包、缺卷和目标占用场景验证新旧历史、来源与输出不被误修改。回滚不完整的保留文件指引优先级不得被新通用指引覆盖。
