# 结构化失败历史：实现与接续

## 范围与需求对齐

延续升级规划第一步的失败类别/阶段落库，服务于“失败后知道为什么、在哪里失败”，不扩展为新功能中心。版本保持 1.3.2，本轮不发布 Release。

- 历史数据库 schema 7 → 8，事务内增加可空 `failure TEXT`。旧行保持 NULL，不根据旧日志回填猜测。
- 新失败保存 schemaVersion、category、stage、evidence。后端依据已确认的检测标记归类，覆盖调用方类别；检测阶段优先于可能过期的进度阶段。
- 无检测标记时类别保持 unknown，仅保存白名单内最后收到的运行阶段；界面明确标注“最后观测阶段”，不等同于确定的故障发生点。
- 成功/取消记录不保留失败结构；同 ID 更新同步替换结构与原因。旧客户端缺省字段、旧行和无法解析的可选结构仍可读取。
- 历史类别筛选、详情及 JSON 诊断报告优先读结构化信息，旧记录保持原标记兼容解析。

## 审计与验证

- 类型检查通过，历史界面/失败描述/任务状态机定向测试 27/27 通过。
- Rust 历史命令测试 12/12：包含真实临时 SQLite 关闭再打开、检测标记覆盖调用方分类、观测阶段更新、成功后移除失败结构。
- 数据库迁移定向测试 4/4，通过两次初始化确认幂等与旧行不回写；1 个依赖关闭的用户数据库快照测试按设计跳过。未触碰用户正在使用的数据库。
- `cargo clippy --lib --tests -- -D warnings` 通过。
- 前端生产构建通过，`git diff --check` 无空白错误。
- Windows CI 和合并证据在完成后补录；不把安装器构建当作所有业务场景验收。

## 尚未完成与下一步

1. 非检测阶段仍大量使用旧字符串错误；本轮完成持久化通道，不代表所有引擎都有类型化错误类别、原始详情和可重试条件。
2. 后续按解压、校验、输出实际调用顺序补充确定的错误代码及定向样本，未知原因继续如实保留。
3. 历史草稿仍不是原配置重试；需要独立设计可恢复的配置快照，不能静默猜测密码、筛选条件或覆盖规则。
4. 历史保存失败后的跨进程恢复尚未实现；当前仅支持进程内保留任务并补写。

本轮未重新运行用户真实损坏样本或手工桌面交互矩阵，不将先前证据重复记作新增验收。
