# 失败任务最终原因与损坏 RAR 识别审计（2026-09-05）

## 用户实际问题

- 最近一批 RAR 在其他解压软件中被报告为文件损坏，Long解压却因为能读到加密条目标记而启动保险箱及内置字典尝试。
- 失败任务的阶段日志会停在失败前一步，历史详情没有独立错误摘要，也没有以最终失败原因为最后一条日志。

## 根因

1. 7-Zip 可以在截断 RAR 的前部读到 `Encrypted = +`，随后以非零状态结束。原逻辑先相信加密条目标记，再判断列表命令是否完整成功，因此把“损坏且前部条目加密”误分类为“需要密码”。
2. 解压调用层捕获异常后先把任务改为 `failed`；任务仓库在进入终态时立即生成并保存历史。页面外层随后才写入 `task.error`，第二次 `failed` 更新又会被终态去重忽略，导致历史中的 `errorMessage` 为空。
3. 后端并非每条返回错误都会同步产生 `error` 级任务日志，因此仅依赖阶段事件无法保证失败记录最后一定带有终态原因。

## 修复

- 加密探测先判断列表命令是否完整成功。只有完整列表中的加密元数据，或明确的“需要密码 / 密码错误”结果才能启动密码流程；带部分加密元数据的非零普通错误直接保留为归档损坏。
- RAR 加密探测失败使用明确用户提示：“RAR 文件损坏或不完整，无法读取完整目录”，不再包装成含糊的密码检测异常。
- 任务仓库新增原子失败入口：先写 `task.error`，再追加最后一条 `最终失败原因：…` 错误日志，最后进入 `failed` 并保存历史。
- 已经进入 `failed` 后若外层补充了更准确原因，会重新 upsert 同一历史记录；旧的终态原因日志被替换，最终只保留最新结论。
- 后端解压命令在返回错误前也发送最终失败原因；历史持久化层对所有 `failed` 记录再次兜底，缺失原因时写入明确的“执行流程未返回具体错误原因”，不再展示空白失败。

## 验证

- 本机同一批仍存在的近期损坏 RAR 共 12 个，逐项执行真实目录探测：12/12 直接返回损坏/不完整，0 个进入密码搜索。验证仅读取目录信息，未写出解压内容，也未记录文件名或密码正文。
- 损坏 RAR 部分加密元数据分类聚焦回归通过；真实本机损坏 RAR 门禁通过。
- 任务失败原子落库、错误摘要、最终错误日志及无原因兜底的前端聚焦回归，与历史详情回归合计 29/29 通过。
- 后端失败历史最终原因兜底测试通过；相关 task-history 回归 11/11 通过。
- TypeScript 类型检查通过；`cargo clippy --lib --tests -- -D warnings` 通过。

## 边界

- 完整且真正加密的归档仍会正常进入密码流程。只有列表命令未完整成功、且错误没有明确说明纯密码需求时才归类为损坏/不完整。
- 历史中已经保存为空错误摘要的旧记录无法凭空恢复当时丢失的系统异常；新产生或重试产生的失败记录会完整保存最终原因。
