# 压缩包浏览中心 A-05.1：归档读取可取消化审计

日期：2026-08-26

版本边界：公开版仍为 `1.1.13`；本工作项位于 `codex/archive-media-roadmap`，不单独升版。

## 开发目标与需求对齐

本步骤只修复 A-06 前的可靠性阻断：压缩包结构读取必须真正可取消、必须有等待上限、失败必须可理解。没有提前开发图片、视频或 PDF 压缩，也没有改变解压/压缩主引擎和发布事务。

| 目标 | 实现 | 结果 |
| --- | --- | --- |
| 取消到达后端 | 前端生成唯一 `browseId`，调用独立取消命令；后端维护请求级原子标记 | 已对齐 |
| 封闭极快取消竞态 | 取消先到时预登记已取消标记，读取命令随后到达会直接结束 | 已对齐 |
| 原生读取协作停止 | ZIP、RAR、TAR 在条目遍历时检查标记；7Z 在可控边界检查 | 已对齐 |
| CLI 子进程可停止 | 通用 7-Zip 元数据命令使用 `kill_on_drop`，取消时停止等待 | 已对齐 |
| 异常归档不无限等待 | 所有浏览结构读取统一设置 30 秒用户等待上限 | 已对齐 |
| 用户能理解结果 | 显示取消按钮和取消提示；错误归类为取消、超时、密码、损坏、不支持与通用失败 | 已对齐 |
| 外层状态不被迟到结果污染 | 保留序列号写回保护；返回归档链时同时发出后端取消 | 已对齐 |

边界说明：Rust 的阻塞库调用无法在任意机器指令处被强制中断，7Z 原生单次元数据读取可能在后台线程中自然收尾；但用户等待会立即结束，结果不能写回，条目循环会检查取消。通用 CLI 路径具备子进程终止语义。本文不把“用户已恢复”夸大为“所有第三方库内部指令已瞬时退出”。

## 预期、首次实际与修正

| 场景 | 预期 | 首次实际 | 修正后实际 |
| --- | --- | --- | --- |
| 内层返回/取消 | 用户返回后底层工作也停止 | A-05 只有序列号丢弃迟到结果，元数据读取仍可能继续 | 请求级取消已传到后端，仍保留迟到写回保护 |
| 异常或极慢归档 | 有明确等待上限 | 没有统一超时，用户只能等待或离开页面 | 30 秒后稳定返回超时分类 |
| 极快点击取消 | 取消不应因登记顺序丢失 | 初版实现存在取消命令可能先于读取登记的竞态 | 取消可预登记；随后读取直接返回已取消 |
| 错误展示 | 用户看到可行动的中文说明 | 页面直接显示底层英文错误 | UI 只显示稳定中文分类，不回显密码或命令行 |
| 桌面门禁启动 | Release 应从打包资源启动 | 第一次只启用 `desktop-e2e`，WebView 指向未运行的 localhost | 按文档用 `custom-protocol,desktop-e2e` 重建后进入真实应用 |
| 大型真实归档取消 | 5 秒内恢复空闲 | 修复前没有可点击取消入口 | 18 万目录项 TAR 点击取消后 55 ms 恢复 |

## 真实测试证据

桌面样本不是 Mock：测试在本机现场写入符合 TAR 头规范的 18 万个真实目录项，总体约 88 MiB，从可见“打开压缩包”进入正式 Tauri IPC，再点击可见“取消读取”。实际从点击到出现“已取消读取压缩包内容”为 55 ms，满足小于 5 秒的验收目标。

同一 Release 会话随后继续验证：中文八层长路径 ZIP、加密 7Z、固定上游加密 RAR、选择性解压、目录/历史导航、刷新保持选择、内部文本预览、TXT/PNG/PDF 默认应用打开、危险 CMD 默认拒绝、ZIP→加密 7Z→ZIP 三层嵌套、第四层阻断、损坏内层返回和最内层精确解压。最终门禁报告 `Real Windows Tauri archive-browser gate passed.`
