# ZIP 下载不完整：用户链回归与修复

## 真实发现

用户场景：“同一批下载里一个包没下完整，另一个是好的。失败要说清楚，不能让我试密码，也不能影响好包。”

使用现有 WebDriver 驱动实际 Tauri 页面；只替代文件选择器返回路径，随后点击页面开始队列。真实 Rust 引擎、事务输出、SQLite 历史均未模拟。夹具为新建中文资料 ZIP 及按字节截断一半的副本，不读取用户私人文件。

修复前该场景失败：最终原因为 `解压失败: 归档检测失败：invalid Zip archive: Could not find EOCD`。原始错误保留了，但用户无法直接理解为结构损坏或下载不完整；缺少结构化损坏标记。

## 修复范围

- `UniversalCliEngine::zip_requires_password` 在打开 ZIP、解析目录和读取原始条目元数据时统一映射类型化错误。
- `InvalidArchive` / `UnexpectedEof` 提示 ZIP 结构损坏或不完整；权限错误、其他读取错误各自标记，未知或不支持特性不猜测为密码错误/损坏。
- 保留原始详情（包括 EOCD 和操作系统读取错误）；复用已有 `archive-inspection` 分类落库、筛选及历史最终原因显示，无 schema 升级。
- 不修改密码候选、解压算法、冲突规则和损坏判断测试断言。

## 同一真实链发现：冲突等待被提前记为失败

完整 ZIP 的输出目录已有 `资料.txt`（夹具原始内容），实际触发了产品冲突弹窗。历史却在选择前出现 `File conflict requires resolution` 的失败记录：`useTauriCommands.decompressFile` 先调用 `failTask` 落库，页面随后改回 pending 为时已晚。

- 在命令包装层将明确的“需用户解决文件冲突”保持 pending，不调用终态保存；继续抛出原信号供页面展示弹窗。
- 磁盘错误等真实失败及取消状态的原有处理保留。
- 新单测先得到 failed 而非 pending（19 通过、1 失败），修复后重新跑全量。
- 保留同名文件冲突，不通过清除冲突夹具规避问题：页面选择“自动重命名保留两者”，逐字节哈希核对 `资料 (1).txt` 与原件；等待选择期间不得写失败历史。
