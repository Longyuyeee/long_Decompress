# 解压任务列表与存储预检界面审计（2026-09-03）

## 基线与范围

- 基线：公开 `v1.2.6` 后续文档提交 `master@438bfad`。
- 开发分支：`codex/decompression-table-layout`。
- 本轮只修复解压任务列表、展开详情和低高度侧栏，不提升版本、不打包、不创建 Release。
- 真实桌面候选使用独立 `desktop-e2e` Release 构建和测试数据；没有停止、替换或复用用户正在运行的 `E:\Long\Long解压\Long解压.exe`。

## 五项需求逐条对齐

| 用户需求 | 根因 | 当前实现 | 审计结果 |
| --- | --- | --- | --- |
| 压缩包名称区域过窄，省略后应可查看全称 | 表头、任务行分别使用不同的 Flex 比例，并在大屏额外插入仅任务行实际需要的路径列 | 表头和任务行共用五列 Grid；名称列最小宽度提高，名称节点使用原始名称作为 `title` | 名称列不再被状态区随意挤压；省略时浏览器/桌面原生悬停提示可读取完整名称 |
| “解压状态与进度”未对齐且存在大片空白 | 状态、运行阶段、当前文件、速度、进度百分比全部进入一个无固定轨道的 Flex 流；终态仍保留运行态空间 | 状态区改成“主状态 / 运行摘要 / 百分比”三轨 Grid；终态切换为单轨并居中；移除折叠行中低价值且造成列错位的物理路径 | 表头、活动态和终态使用同一状态列；终态居中，活动态不互相挤压 |
| 多文件导入后按名称自动排序 | `displayTasks` 直接保留任务插入顺序 | 使用 `Intl.Collator('zh-CN', { numeric: true })` 对过滤后的任务做自然名称排序，名称相同时以任务 ID 稳定兜底 | `-2`、`-10`、`-20` 顺序通过回归，不再出现字典序的 `-10` 排在 `-2` 前面 |
| 存储预检太小、内容不全 | v1.2.6 为压缩详情高度把预检压成单行，只剩状态和可用空间 | 紧凑卡恢复位置/介质、剩余可用、预计占用、挂载点、文件系统和预留空间，并前移到输出目录之后 | 760×520 真实桌面截图中完整卡片可见，纵向滚动可达，无横向溢出 |
| 左下角版本标识消失 | `@media (max-height: 640px)` 直接把 `.sidebar-version-row` 设为 `display: none` | 低高度仅压缩版本行高度和间距，不再隐藏 | 920×620 显示完整 `LONG解压 / v1.2.6`；760×520 紧凑侧栏仍显示 `v1.2.6` |

## 实际观察与纠偏记录

1. 首轮真实 Windows Tauri 门禁在 920×620 测得解压配置栏只有 245 px，低于 250 px 可读性底线；调整断点比例后，760×520 又测得 248 px。最终按实际可用宽度使用 `.92fr / 1.08fr`，两档均通过，未降低门禁阈值。
2. 首轮 Chromium 760×520 回归发现恢复后的预检卡虽然存在，但只露出边缘并被底部操作区遮挡。实现随后把预检卡前移到输出目录后；测试也改为先将真实卡片滚动到视口，再要求至少 70% 可见，而不是只检查 DOM 存在。
3. 最终真实 Tauri 760×520 截图中，预检卡完整显示 `剩余可用 106.0 GiB`、`预计占用 780.0 MiB`、`C:\ / NTFS / 预留 128.0 MiB`；左侧紧凑版本徽标显示 `v1.2.6`。
4. 920×620 与 760×520 的配置/执行双栏保持同高，详情、配置、执行、日志和预检横向溢出均不超过 1 px；日志仍由自己的纵向滚动区承载。
