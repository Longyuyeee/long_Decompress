## 1. 最初需求对齐

| 要求 | 实际实现 | 状态 |
| --- | --- | --- |
| 复用统一任务系统 | 每个视频写入现有 task store，`workloadKind: video`；没有第二套队列、历史表或进度监听器 | 通过 |
| 执行前风险可见且显式确认 | 工作区继续显示后端流变化；批量启动前用系统确认框逐文件列出变化，拒绝时不规划目标、不创建任务、不调用编码 | 通过 |
| 安全目标规划 | Rust 在源目录或用户选择目录生成 `.compressed.mp4`；真实既有文件和本批保留路径均自动递增重命名，发布竞态仍由共享事务失败关闭 | 通过 |
| 真实进度展示 | 统一 task store 保存当前媒体时间、速度倍数、临时输出大小/比例、ETA 和最后心跳；UI 明确区分“临时输出”和“最终输出”，心跳显示“仍在编码” | 通过 |
| 统一取消 | 当前子任务只通过 `taskStore.cancelTask` → `cancel_compression`；取消后停止后续批量项，任务为 cancelled，后端负责进程树与暂存清理 | 通过 |
| 验证后才完成 | `compressVideoFile` 返回 `PublishedVideoOutput` 后才写 100%、completed 和成功日志；FFmpeg 进度到 100% 不触发完成 | 通过 |
| 最终指标与历史 | 输入/输出字节、节省比例、可见尺寸、时长、H.264/AAC/MP4 仅由发布事实生成 `TaskMetricsV1`，并等待统一历史写入；后端历史校验接受并保留这些视频事实 | 通过 |
| 源文件保护 | 当前视频工作区没有回收源文件开关，不读取归档的自动删除设置；视频源始终保留 | 通过 |

## 2. 审计发现与修正

- 全局进度条原有失败重试逻辑把所有 compression 任务都按归档命令重试。媒体任务开放后会把失败视频误送到归档压缩。本节点限制该快捷重试仅适用于旧 archive/缺省工作负载；图片和视频从各自工作区以完整设置重新执行。
- 批量目标保留数组最初直接传给异步命令后继续修改，测试 spy 会观察到变更后的引用。现改为传递快照，调用契约与审计记录稳定。
- 视频历史等待结果最初没有消费布尔返回值。现与图片批量一致：任何历史写入失败都会让批量摘要明确报错，不能静默宣称整个批量闭环成功。
- 取消可能发生在当前项完成目标规划、尚未注册后端编码命令的短窗口。批量适配器现在在规划返回后再次检查停止标记，将该准备中任务直接结束为 cancelled，绝不因取消注册表尚无活动令牌而继续启动编码。
