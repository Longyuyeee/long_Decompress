# v1.7.41 · Windows 文件右键菜单核对与整理

本次针对 Windows 文件资源管理器，尤其用户确认的“显示更多选项 → Long解压”经典子菜单。不是双栏浏览器内的右键菜单。候选版本为 v1.7.41，尚未正式发布；本机旧安装版本不能解释另一台新版本电脑的反馈。

## 复现与原因

旧设计在通用文件 `*` 和 `SystemFileAssociations` 下分别注册同名的 Long解压级联菜单。之前仅核对某一注册树、命令数组和 COM 状态，没有覆盖它们同时参与 Windows 菜单生成的情况。

这次用 Windows `SHCreateDefaultContextMenu` 生成真实 HMENU，并将通用和压缩包关联同时交给 Shell，复现了两个同名 Long解压子菜单：前一个只有通用压缩操作，后一个才有压缩包完整操作。仅点击第一份，就会产生“新版本也远远没有列出的功能”的现象。这个复现解释了一条实际缺失路径，不宣称已远程检查用户另一台电脑。

另发现 Windows 11 稀疏包声明只包含独立快捷命令，未注册完整菜单根；原生菜单遗漏校验操作，并把维护入口放在嵌套层内。启动重试原本也会重复删除、重建已经完整的菜单，存在与设置同步交错的窗口。

## 菜单结构

经典菜单现在由一个 IExplorerCommand 提供器根据实际选择生成。通用文件和文件类型不再各注册一份同名菜单；清理旧注册，使用版本独立的 `long_compress_shell_extension_1_7_41.dll`，避免 Explorer 复用旧扩展。所有命令继续交给现有任务、浏览和工具功能处理。

| 所选内容 | Long解压子菜单 | 完整功能数 |
| --- | --- | --- |
| 普通文件 | ZIP、7Z、添加到压缩包、加密、分卷、生成校验清单 | 6 |
| 文件夹 | ZIP、7Z、添加到压缩包、加密、分卷 | 5 |
| 压缩包 | 浏览、此处/同名目录/自选目录解压；**压缩打包**内收纳 5 项压缩；**更多操作**内收纳完整性、修复、格式转换、密码/分卷；生成校验清单 | 14 |
| JPG/JPEG/PNG/WebP | 压缩图片、转换 WebP、缩小尺寸；**压缩打包**内收纳 5 项普通压缩；生成校验清单 | 9 |
| SFV/MD5/SHA256 清单 | 核对清单；**压缩打包**内收纳 5 项压缩；生成校验清单 | 7 |

数量按可执行叶子命令计算，不把分组标题当成额外功能。文件夹不提供按普通文件计算的校验清单；混合选择保留共同适用操作，单包浏览只对单个压缩包提供。恢复卷沿“更多操作 → 检查与尝试修复”。

Windows 11 原生入口使用同一动作范围、按顺序分区的一层命令，避免依赖嵌套维护入口。完整根命令加入包清单；原生入口需要有效应用身份，未部署时完整菜单仍在“显示更多选项”。不把修改包清单等同于已验证公开签名部署。[微软关于入口和身份的说明](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer)。

## 注册与设置

- 注册、移除、就绪检查和启动刷新共用锁，完整时跳过重建；只有所有必要注册匹配当前可执行文件和扩展路径后才报告成功。
- 旧静态级联不能被误判为当前完整菜单。关闭集成时也移除残留的部分注册；卸载清理新 CLSID 和新增清单类型入口。
- 设置中明确叫“Windows 文件右键菜单”，紧凑展示完整菜单实际位于哪里，并提供“修复菜单”。修复失败保留启用偏好，显示失败状态；不需要先关再开。
- 原有单条展开、多选弹窗和等宽双栏保持。

## 核对边界

菜单检查使用真实 Windows Shell、实际编译的扩展 DLL、COM 接口和独立参数接收程序；仅在独立测试注册树中工作，预定义键映射和 COM 工厂注册限定于测试进程，不控制桌面、不改真实文件关联或安装程序。逐项执行验证的是 Shell 命令派发及精确输入路径；压缩算法、图片编码和恢复引擎复用 v1.7.40 已有检查，前端路由和预设沿相关测试核对，不把派发检查宣传为重新测试所有算法组合。

核对完成：实际 Windows Shell 的五类菜单、41 次菜单叶子调用及标签到命令映射通过；六项 COM 检查包含 19 个命令的独立进程参数接收，覆盖中文、空格、多选和混合选择。相关前端共 49 项通过；1280×720、920×720 两个设置场景通过，最终截图实看通过。前端生产构建、原生主程序检查、Shell DLL 构建、八处版本身份、三份包定义和七份 PowerShell 语法检查通过。安装/公开更新矩阵和签名部署没有重新执行，相关脚本已同步识别新经典提供器。

首次类型树单独检查通过后，加入通用关联的检查明确失败，才定位同名重复问题。最终同时确认每类只有一个 Long解压根、分组正确、没有开头分隔线、全部叶子可派发、目标版本一致。初次浏览器冷导航超时，补齐关联状态测试数据后最终两个场景通过；没有重跑无关格式矩阵。
