## 本轮实际取得的东西

从 [unalz 作者保存的旧版工具](https://kippler.tistory.com/164)取得三份安装器，用 [innoextract 1.9](https://constexpr.org/innoextract/)解到项目临时目录，不运行安装器。所需 sys 文件只复制到对应的临时 app 目录，没有复制到 Windows 系统目录。版本取自解出的 `ALZip.exe` 文件元数据，不由下载文件名推断；历史备份也不冒称当前官方签名发行源。

| 备份文件名 | 程序报告版本 | 本轮生成方式 | 实际结果 |
| --- | --- | --- | --- |
| ALZip55.exe | 5.3.0.378 | 帮助文件记载的 `ALZip -a <文件> <新包.alz>` | 16 个方法 2 条目 |
| ALZip_eng_55.exe | 5.5.0.645 | 同上 | 16 个方法 2 条目 |
| ALZip56.exe | 5.6.1.9 | 同上 | 16 个方法 2 条目 |

三组使用同一份自有公开载荷：16 个文件分别为 4096～4111 字节，覆盖未压缩大小模 16 的全部取值。没有修改归档头、注入流或自制方法 3 编码器。三份生成物逐字节相同，只保存[一份方法 2 原件](evidence/alz-method3-source-1.6.5/original-default-method2.alz)，SHA-256 为 `9a593c7ae140923e386db0e7426980c5a5978272155774d73d2fd6626f30291d`。现有 helper 回解的 48 个输出均与自有来源哈希一致。

这只证明**上述三个构建、当前环境下该默认命令和这些载荷**得到方法 2。没有穷举 GUI 选项，没有验证方法 3 的密码或分卷；不能由此断言这些版本所有选项都无法生成，也不能把现有 helper 的方法 2 回解写成方法 3 的独立互通验证。首次整理记录时有一次 Python 字典排序错误，未计为新验证；保留已生成原件与已完成回解，只补齐记录，不重新造包。

工具、参数、归档和源文件身份见[调查收据](evidence/alz-method3-source-1.6.5/producer-probe.json)。工具二进制不随 Git 分发。可在项目根目录准备收据所列的三个解包目录及依赖后运行 `node scripts/probe-alz-method3.mjs`；已有产物会保留。`--inspect-only` 只读取本机本轮产物、已解出的文件和工具哈希，不重新执行生成或解压。新机器生成的时间戳可能不同，应另记原件身份，不能覆盖这份收据冒充同一次调查。

## 为什么没有直接开放方法 3

[格式调查](https://github.com/mietek/theunarchiver/wiki/AlZipSpecs)和 [XADMaster 的分派实现](https://github.com/MacPaw/XADMaster/blob/1da801bff196f70c1abab41d49580a56c9af2e8d/XADALZipParser.m)说明它改变动态 Huffman 码长表顺序，参数与未压缩大小的低四位有关；[Bandisoft](https://en.bandisoft.com/bandizip/help/how-to-open-alz-and-egg-files/)列出其解码支持。这些资料可以指导实现调查，但不是本产品读取真实方法 3 文件成功的证据。本轮没有引入这些项目的代码或新增解码依赖。

当前 ALZ 路由仍明确拒绝方法 3，不把它当作普通 Deflate，不进入重复试密。此前 v1.5.12 的官方新工具取材和完整性检查保留，不重跑；其最高档请求没有生成方法 3 原件的事实仍有效，但同样不代表所有工具版本都不可能生成。

## 接下来按条件推进

1. **补足来源**：优先寻找能实际生成方法 3 的明确旧构建或未修改的历史原包。记录取得位置、工具真实身份和归档哈希。历史包若缺创建参数/原始树，明确缺项，用独立读取器逐文件固定载荷，仍不能外推密码、原生卷或所有组合。
2. **普通单包解码**：有正面原包后实现并核对真实数据边界、结束条件、大小和 CRC；跨大小余数和多块的覆盖按原件实际内容建立，派生损坏件单独标注。
3. **密码及原生卷**：分别取得对应方法 3 原件后接原代码页、补密码、缺卷提示和失败新任务。不能用方法 2 的既有通过记录代替这些组合。
4. **用户流程收尾**：双栏内浏览、常用文本/图片预览、所选/整包提取、转换及结果；保留单条展开、多选弹窗、左右等宽。只补本次变更所需的运行和宽窄显示。

以上不是四次空版本；有可独立使用且证据足够的增量后再确定发布范围。来源阶段未完成时不升级版本身份、不写“已支持”，也不反复执行现有旧样本或打包来代替开发。

后续 EGG 加密固实也必须先取得真实组合。v1.5.11 已记录原 ALZipCon 11.0.1.16 的 20 个加密固实请求被拒绝，本轮不重复这组矩阵。先找不同且可确认的生成工具/版本及实际组合，不能把现有“加密”和“固实”两项单独支持相乘为全组合支持。它仍是条件候选，不能当作已具备封板来源的紧接版本。
